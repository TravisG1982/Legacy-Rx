# Agent rules

## Current implementation versus approved launch direction

- The current new-order code uses FuseHealth's Brand API hosted intake + payment (`POST /checkout/sessions` from `/start/$med`); program IDs live in `FUSE_PROGRAM_IDS` and products without one are hidden. The route currently redirects to FuseHealth's hosted form. FuseHealth remains for the existing flow until the Beluga replacement has been tested end to end.
- For the LegacyRX launch, the client chose Beluga's branded **hosted medical intake forms**, integrated through Beluga's API and webhooks. The client reports that patients remain on the LegacyRX website. LegacyRX controls Stripe checkout/payment processing, patient accounts, and dashboards. Confirm Beluga's actual hosted-form/session contract and payment authorization/capture timing in documentation and sandbox. A fully direct API intake is a later option, not launch scope. Beluga's 30-day hosted-forms estimate is not the whole-app launch date.
- Keep the three LLCs' production patient data, payment accounts, infrastructure, access, and vendor agreement coverage separate. Do not use real patient information before the required agreements and safeguards are in place.

## Existing code paths and conventions

- `FUZERX_API_KEY` is the live FuseHealth Brand API key despite its name; do not remove or rename it without a coordinated secret change. FuseHealth webhook events are recorded in `orders.provider_last_event` (migration `20261026120000`); the old `fuzerx_last_event` column is no longer written.
- Order status updates arrive on `/api/public/webhooks/fuse-brand`, verified with `X-Fuse-Signature` and deduped by `X-Fuse-Idempotency-Key`; rows match by `fuse_order_id` or `fuse_session_id`. Why: Fuse webhooks carry only opaque ids, so the row is created when the session starts.
- Customer accounts match orders by verified email (as well as `user_id`). Why: checkout doesn't require sign-in, so guest orders still appear after sign-up. Legacy subscriptions remain in the database but are no longer shown in the account.
- The old Stripe checkout, Stripe webhook, FuzeRx fulfillment/webhook, coupons and subscription/billing-portal code were removed on 2026-10-26 (decision: Lovable-era records are not migrated; their backup is kept outside this repo). The Stripe SDK stays in `package.json` for the new LegacyRX-controlled Stripe and Beluga flow, which must be built fresh and must not reuse the removed subscription/charge code. Why: that code had no working scenario and no verified payment contract. Legacy columns/tables (`fuzerx_*`, `stripe_*`, `coupon_code`, `subscriptions`, `coupons`) remain in the database until a separate reviewed cleanup.
- A separate **test-mode** LegacyRX Stripe path exists (`/pay-test/$med`, `/api/public/webhooks/stripe-test`, tables `payment_test_orders` and `payment_test_webhook_events`, `src/lib/stripe-test*.ts`). It never touches `orders`/FuseHealth, refuses any key that is not `sk_test_`, and requires a signed-in verified account matching `STRIPE_TEST_ALLOWED_EMAIL`. It takes the amount only from the server catalog, sends no product or medical details in our Stripe request, and moves statuses through `apply_payment_test_event()` (idempotent by Stripe event id). The private result URL uses the explicit `STRIPE_TEST_RETURN_ORIGIN`. Authorization/capture timing is provisional (`STRIPE_TEST_CAPTURE_METHOD`) pending Beluga; subscriptions/renewals are out of scope. Setup: `STRIPE_TEST_SETUP.md`. Why: the payment contract with Beluga is unconfirmed, so this is a replaceable test harness.
- Unpaid orders older than 24h are swept to `abandoned` lazily (on /travis load). Why: no cron needed.
- Products are defined in `legacyrx-data.ts` (`MEDS`, `MED_INFO` with a `track`; a product is offered only when it has a `FUSE_PROGRAM_IDS` entry). Why: catalog products are added by data only; qualify, `/start/$med` and pages read from it. There are no promo codes or discounts.
- Non-GLP-1 programs reuse `/qualify?track=<trt|hrt|aa|sh>` with per-track screening; screening answers are stored and verified server-side by the assessment step before `/start/$med`. Why: one funnel, one checkout.

- Use semantic medical-red and ivory brand tokens as the visual source of truth across shared pages and scoped campaign palettes. Why: the customer experience must maintain one consistent LegacyRx identity.
- Blog articles live in the typed `blog-data.ts` catalog and render through one dynamic route. Why: listing cards, metadata, and article pages stay synchronized as content grows.
- The order helper (`OrderHelp` in FunnelShell and the verified account) uses fixed, non-medical questions and answers. Specific order status is fetched from our database only after server-side authentication, verified-email, and ownership checks. Why: customer text and order details must not be sent to OpenAI.
